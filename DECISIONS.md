## Milestone 1

- **M1-01 Test database.** Tests use a local Postgres 16 server, not a container (no Docker daemon in the build sandbox). `sqlx::test` creates a fresh throwaway database per test and applies `/supabase/migrations`. `.cargo/config.toml` (repo root, so it applies from the root and from `axom/`) defaults `DATABASE_URL` to `postgres://axom:axom@localhost:5432/axom`; set `DATABASE_URL` to override. The self-hosted Supabase dev instance uses the same migrations.
- **M1-02 Schema.** All ForeMan tables live in a Postgres schema named `axom` (keeps them apart from Supabase's `auth`/`storage` schemas). Migrations are embedded with `sqlx::migrate!` as `axom_core::MIGRATOR`.
- **M1-03 Queries.** Runtime-checked `sqlx::query` (not the compile-time macros) so the workspace builds without a live database.
- **M1-04 Money.** USD amounts are `rust_decimal::Decimal` in Rust and `NUMERIC(18,6)` in Postgres. No floats for money.
- **M1-05 Audit log immutability.** Enforced in the database: triggers reject `UPDATE`, `DELETE`, and `TRUNCATE` on `axom.audit_log`.
- **M1-06 Audited invalid transitions.** `axom_core::db::transition` rolls back the failed transaction, then writes the `rejected` audit event on a separate connection so the record survives the rollback.
- **M1-07 State machines.**
  - Task: queued → assigned/blocked; assigned → in_progress/queued/blocked; in_progress → done/failed/blocked/queued; blocked → queued/assigned/in_progress/failed; failed → queued (retry); done is terminal.
  - Worker: initial candidate (humans) or active (AI agents, hired autonomously). candidate → active/fired (a rejected candidate ends as fired); active ↔ on_probation ↔ suspended; anything → fired; fired is terminal.
  - Payout: initial pending_approval, approved (automatic under-threshold attestation), or cap_exceeded. pending_approval → approved/rejected/expired; approved → sent/failed; sent → finalized/failed; failed → sent (retry). finalized, rejected, expired, cap_exceeded are terminal, so approval can never move a cap_exceeded payout.
- **M1-08 Policy file and version.** `config/policy.toml` holds the rules and a human-set `version`. Env vars `PAYOUT_APPROVAL_THRESHOLD_USD` and `MONTHLY_PAYOUT_CAP_USD` override the matching values. The recorded policy version is `<version>+<first 8 hex of sha256(effective config)>`, so a decision always identifies the exact values used, including env overrides.
- **M1-09 Cap storage.** The cap lives in `axom.cap_settings` (single row). First boot seeds it from config/env; it is never overwritten by config after that. Only `cap::change_cap` with an MFA-verified admin actor changes it; every attempt (applied or denied) is audited, and applied changes are also recorded in `axom.cap_changes`.
- **M1-10 Cap locking.** Each UTC month has a row in `axom.cap_months`. Reserve, commit, and release lock it `FOR UPDATE` (and the cap row `FOR SHARE`) inside the caller's transaction. Ledger entries are `reservation`, `commit`, `release`, at most one of each per payout. Month usage = reservations − releases (open reservations + commits). Commit and release always use the reservation's month and full amount.
- **M1-11 Cap amount.** The amount reserved is payout USD + network fee USD (fees count toward the cap). A payout row is inserted first, then reserved in the same transaction; on cap_exceeded the row is kept with status cap_exceeded and nothing is reserved.
- **M1-12 Rolling 24-hour aggregation.** Sums `amount_usd` (excluding fee) of the recipient's payouts in statuses pending_approval, approved, sent, finalized, failed created in `(now − 24h, now]`, plus the new amount, then compares to the threshold (≥ threshold → approval). Payouts to the same recipient serialize on a transaction-scoped advisory lock so concurrent splits can't both slip under.
- **M1-13 Price feed.** The policy engine takes an optional `PriceQuote` (USD per NEAR + fetch time). Missing, future-dated, or older than 900 s → require_approval. The feed client itself is built in milestone 4.
- **M1-14 Policy denial of payouts.** A denied payout (kill switch, bad amount) creates no payout row; the denial is audited only.
- **M1-15 Kill switch.** Stored in `axom.system_controls` (single row). When on, the policy engine denies every non-protected action. A missing row is treated as kill switch on (fail closed). Admin-only actions (e.g. turning it off) still evaluate.
- **M1-16 Protected actions.** approve_payout, change_cap, change_policy, change_tool_allowlist, change_wallet_settings, and toggle_kill_switch are allowed only for `Actor::Admin { mfa_verified: true }`. In milestone 1 the MFA flag is set by the caller; milestone 4/7 derive it from the Supabase Auth session in axom-api.
- **M1-17 Owner notifications.** Milestone 1 records notifications in `axom.owner_notifications` (cap_exceeded so far). Delivery (SMTP + dashboard feed) is milestone 3.
- **M1-18 Approval expiry.** `payouts::expire_pending(now)` expires pending approvals created ≥ 7 days ago and releases their reservations. A scheduler calls it (wired in milestone 4).
- **M1-19 HR agent proposals.** LLM output is parsed into a closed `Proposal` enum; unparseable output is discarded. Every proposal runs as `Actor::Agent` through the same functions the dashboard uses, which re-check the actor, and is audited. The injection test uses a worst-case "gullible" model stub that obeys the message, to show the gate holds even when the model is fooled.
- **M1-20 Untrusted data.** `axom_core::untrusted::Untrusted` renders content only inside `<<<UNTRUSTED_DATA source="…">>> … <<<END_UNTRUSTED_DATA>>>`, and neutralizes `<<<`/`>>>` inside the content so it can't close its own block.
- **M1-21 Human workers and tools.** A task is a tool-execution task when it requires any tool. `Worker::covers` never matches a human worker to one, and a DB check constraint forbids a non-empty tool allowlist on human workers.
- **M1-22 search_path.** The app pins `search_path=public` on its connections. With Postgres's default `"$user", public`, a role named `axom` resolves unqualified names into the `axom` schema once it exists, so sqlx's `_sqlx_migrations` table moved and migrations re-ran on the second boot. Found by booting twice; all ForeMan SQL is schema-qualified anyway. Tests are unaffected (sqlx::test databases are fresh), but any other tool connecting as `axom` should set the same search_path.

## Milestone 2

- **M2-01 Planner.** The default planner (`RuleBasedPlanner`) is deterministic and driven by the versioned `config/planner.toml`: each objective maps to a department template by explicit `department` hint, else most keyword hits (ties by config order), else `fallback_department`. Only departments with objectives are created. One first task per objective; priority 1,1,2,2,3… by objective order (max 5); deadline is the plan deadline. An LLM planner can implement the `Planner` trait later; its output must pass the same `validate`.
- **M2-02 Proposal validation.** Before saving: goal and objectives present, budget ≥ 0 and ≤ the current monthly cap, unique non-empty department/team/role names, human roles have no tools, every tool is in `known_tools`, pay rates ≥ 0, headcount ≤ 10 per role, tasks reference a proposed department with priority 1–5. A rejected proposal saves nothing and is audited (`plan.boot` / `rejected`).
- **M2-03 Idempotent boot.** Boot takes a transaction-scoped advisory lock, and if any plan is stored it is reused with its org chart. If the plan file's content hash differs from the stored plan, the stored plan still wins and the mismatch is audited (`reused_stored_plan`); replacing a plan is a future admin action. Concurrent boots produce one org chart (tested with four parallel boots).
- **M2-04 Workers at boot.** AI-agent roles are instantiated at boot as active workers (`<title> #n`), each an autonomous AI hire evaluated by the policy engine and audited (`worker.hire`). The daily digest is milestone 3/7. Human-freelancer roles are stored as roles only; routing opens hiring requests for their tasks, filled in milestone 8.
- **M2-05 Routing.** Eligible workers: status active or on_probation, tools ⊆ allowlist, skills ⊆ skills, and never a human for a tool-execution task (also re-checked at the write and by a DB constraint on human allowlists). Lowest load wins (load = tasks assigned, in_progress, or blocked); ties go to the earliest-created worker. Routers serialize on a session advisory lock.
- **M2-06 Hiring requests.** At most one open hiring request per task (partial unique index). Kind: tool-execution tasks → ai_agent; otherwise human_freelancer if a planned human role covers the skills, else ai_agent.
- **M2-07 Adapter traits.** Defined in axom-tools now for every adapter in milestone 5 plus a generic `ToolExecutor`. Every outbound method takes `Authorized`, which can only be built from an `allow` policy decision. Errors are typed (retryable, permanent, rate_limited, not_authorized). `MockTools` implements every trait, records calls with the policy version, and makes no network calls. Vendor API checks happen in milestone 5.
- **M2-08 Mock-tool runner.** For an AI worker, each required tool is checked with `ExecuteTool` against the worker's allowlist (and the kill switch) before the task starts; a denial blocks the task. Tool output is stored in the task result as `untrusted_content` and never parsed. Human workers' tasks are sent as briefs through `TaskIntake` (authorized as the system's `task_intake` tool) and move to in_progress.
- **M2-09 Binary.** `axom` (axom-bin) loads policy, planner config, and the master plan from paths in env (`AXOM_POLICY_PATH`, `AXOM_PLANNER_CONFIG_PATH`, `AXOM_MASTER_PLAN_PATH`), migrates, seeds the cap, boots, routes, runs mocks, and serves read-only API routes (`/health`, `/org-chart`, `/tasks`, `/cap`). `AXOM_LIVE=true` is refused until live adapters exist.
- **M2-10 Sample plan.** `config/master_plan.json` is a small "Launch a SaaS product in 90 days" plan (budget 450 USD) used by the M2 test. Full seed data is milestone 9.

## Milestone 3

- **M3-01 Crate layering.** `Decision`/`Outcome` moved to `axom_core::decision` (re-exported from `axom_hr::policy`), so axom-tools depends only on axom-core and axom-hr can use the adapter traits (Mailer). Routing moved from axom-planner to `axom_hr::routing` (re-exported as `axom_planner::routing`) because firing reassigns through it. Layering is now core ← tools ← hr ← planner ← api/bin.
- **M3-02 Migrations rebuild.** `axom-core/build.rs` watches `/supabase/migrations`: `sqlx::migrate!` embeds files at compile time and Cargo did not rebuild when a migration was added, so a stale schema ran. Found when the workspace test run failed but per-crate runs passed.
- **M3-03 Task records.** New task columns: `finished_at` (set when a task reaches done or failed; `completed_at` stays done-only), `objective_check_passed`, `llm_quality_score` (0..1), and `llm_judge_model`. Workers gain `model` and `fired_at`.
- **M3-04 Metrics.** Per worker over tasks finished in a window: completion rate = done / (done + failed); on-time rate = done on or before the deadline (UTC date; no deadline counts as on time) / done; cost per completed task = total cost of finished tasks, including failed ones, / done; objective quality = checks passed / checks recorded. A metric with no data is skipped. A window with no finished tasks is never below threshold.
- **M3-05 Objective vs LLM.** Only objective metrics decide `objective_below`. The mean LLM score is stored on the review and shown in notifications as `llm_quality_informational`, but no code path uses it for probation or firing, so an LLM score alone can never fire anyone.
- **M3-06 LLM judge independence.** `record_llm_quality` rejects a judge whose model name equals the worker's `model` (case-insensitive). Human workers have no model, so any judge is fine.
- **M3-07 Review schedule.** A review period starts at the end of the worker's last periodic review (or when the worker was created). A review is due when `every_finished_tasks` (10) tasks have finished in the period, or `period_days` (7) have passed, whichever comes first. Each review covers its whole period, and every review is stored and audited. Config: `config/performance.toml`, versioned as `<version>+<hash>` like the policy.
- **M3-08 Firing rule.** Fire only when all of these hold: at least 10 completed tasks in total, at least 14 days of data (measured from the worker's first finished task to now), and the last 2 periodic reviews (final reviews excluded) both below threshold on objective metrics.
- **M3-09 Probation.** One below-threshold review moves an active worker to on_probation. A later review with data that meets the thresholds moves them back to active. Probation is only a status and never fires anyone by itself.
- **M3-10 Firing execution.** In this order: policy `Fire` check; a `final` review over the worker's whole history; then in one transaction: status → fired (state machine), allowlist cleared and the revoked tools recorded, open tasks (assigned, in_progress, blocked) moved back to queued with no assignee, a `worker.fire` audit event (reason, metrics, final and last review, reopened tasks), and the owner notification. After commit, `route_queued` reassigns the reopened tasks; those nobody covers get hiring requests.
- **M3-11 Kill switch and firing.** Firing is a policy-checked action, so it is denied while the kill switch is on (consistent with "halt everything"). It runs on the next review cycle after the switch is turned off.
- **M3-12 Owner notifications.** The notification row is written in the same transaction as the event, so it exists the moment the event commits. Each row is the dashboard feed entry (`GET /notifications`; UI in milestone 7). The binary emails pending rows every 15 seconds through the `Mailer` trait (mock in dry-run; SMTP adapter in milestone 5), which is well inside one minute. Delivery tries up to 5 times per row; after that the row stays in the feed with `last_error`. The audit link is `<AXOM_DASHBOARD_URL>/audit/<audit_id>`.
- **M3-13 NotifyOwner action.** New policy action, allowed even under the kill switch so the owner always hears what happened, but only to the configured `AXOM_OWNER_EMAIL`. If the owner email is unset, delivery is refused and notifications stay in the feed.
- **M3-14 Spot checks.** A review goes to the owner's spot-check queue when the first 8 bytes of sha256(review id), read as a fraction, fall below `spot_check_rate` (0.10). This is deterministic per review and uniform because review ids are random v4 UUIDs; final reviews are never sampled. The owner answers agree or disagree, as an MFA-verified admin. `spot_check_stats` reports sampled, answered, disagreements, and the disagreement rate (also at `GET /spot-checks/stats`).
- **M3-15 Review loop.** Lives in axom-bin for now (every 15 seconds: run due reviews, then deliver notifications). A dedicated scheduler can replace it later.

Then `testnet_payout_sent_and_finalized` ran payroll (1 task × 0.05 USD), the signer verified the automatic attestation and sent 0.0125 NEAR via OpenBao transit signing: tx `BuHCmbFrZ8ej65ZrTZuxf369jSFNpvh1DPNoEj42FTZB`, confirmed independently via RPC as FINAL / SuccessValue, and the recipient balance matched. This closes check (1) end to end: NEAR testnet accepts transactions signed by the OpenBao transit key over `sha256(borsh(tx))`. The dev OpenBao key is ephemeral, so the treasury's leftover testnet balance (~0.98 NEAR) is stranded when the sandbox ends. That is expected for a test key. The VPS uses a persistent, non-dev OpenBao.
- **M4-00a Testnet top-up tool.** `axom-signer/examples/testnet_fund.rs` stands in for the owner's cold-wallet top-up on testnet: it signs a transfer with a local key, refuses non-testnet RPC URLs, and caps a top-up at 5 NEAR. It is not part of ForeMan's runtime; ForeMan never holds the cold wallet key.
- **M4-00b Setup race.** Config-declared audit devices register a moment after OpenBao reports healthy, so `setup-treasury.sh` waits up to 10 s for the `file/` audit device before refusing.
- **M4-01 The three pre-payout checks.**
  - (1) Transit signing yields valid NEAR signatures: with real OpenBao 2.7.1 (dev mode in tests), the transit ed25519 signature over `sha256(borsh(tx))` verifies with the key and is accepted by the node-like validator. Our Borsh encoding matches an independent implementation byte for byte (golden vector from `near-api-py`).
  - (2) The public key maps to the implicit account: lowercase hex of the 32 raw key bytes OpenBao returns; checked in tests and against `setup-treasury.sh` (shell) and the running signer (Rust).
  - (3) Sealed fails safe: with OpenBao sealed, the signer pauses, nothing is signed or marked sent, attempts are not counted, and payouts resume after unseal.
  - NEAR testnet acceptance: verified live (M4-00).
- **M4-02 OpenBao 2.x audit devices.** OpenBao 2.x refuses to enable audit devices through the API ("use declarative, config-based audit device management"). The audit log is declared in `infra/openbao/openbao.hcl`, and `setup-treasury.sh` refuses to continue without it. Found by running against the real binary. The test asserts sign requests appear in the audit log.
- **M4-03 OpenBao setup.** The owner runs `infra/openbao/setup-treasury.sh` with their admin token. It creates `transit/keys/axom-treasury` (ed25519, `exportable=false`, `allow_plaintext_backup=false`, `deletion_allowed=false`), uploads `axom-signer.hcl` (update on `transit/sign/axom-treasury`, read on `transit/keys/axom-treasury`, nothing else), prints the treasury implicit account, and issues an orphan periodic token for the signer. Tests confirm the signer token gets 403 on create, rotate, config, delete, export, and policy read, and that even root cannot delete or export the key. OpenBao binary in tests: v2.7.1, checksum verified against the release's `checksums.txt`.
- **M4-03a OpenBao tokens are never stored in token files.** The signer reads `OPENBAO_TOKEN` and the API reads `OPENBAO_PROVISIONER_TOKEN` from the environment only; the `*_TOKEN_FILE` variables were removed (the signer refuses to start, and the provisioner is disabled with an error, if one is still set). Locally, `./scripts/setup` writes the signer token into the git-ignored `.env` and moves an older `secrets/openbao_signer_token` there; the one-time root token stays in memory. Docker Compose and `scripts/dev.sh` give each token only to the process that uses it. Coolify takes both from its environment editor, and judge mode keeps them in shell variables. The unseal key still lives in `secrets/` (testnet, own machine only).
- **M4-04 Authorizations.** Signed with ed25519, with domain-separated JSON payloads (`axom-payout-authorization:v1:`) covering kind, payout id, network, recipient, yocto and USD amounts, policy version, approval id and approver, issue and expiry times. Automatic attestations are signed by axom-hr (`AXOM_ATTESTATION_SIGNING_KEY`, 24 h validity); human approvals by axom-api (`AXOM_APPROVAL_SIGNING_KEY`, 7-day validity). The signer holds only the two verify keys, so neither a database edit nor a compromised signer can mint one. The seeds are env secrets: they are not the treasury key, which never leaves OpenBao. `axom keygen` makes key pairs.
- **M4-05 Signer checks (before every sign request).** Kill switch off; network matches; status approved, or failed with retries left; authorization present, with a valid signature from the right key for its kind, not expired, and fields equal to the payout record; recipient is a verified, unrevoked address of the payout's worker; tax form on file; open cap reservation. Automatic attestations are re-evaluated with the policy engine as of creation (price age, 24 h window) and must have no human decision. Human approvals must match an approvals row by an active admin with `mfa_verified`. Any failure means nothing is signed, the rejection is audited, and the owner gets a `signer_rejected` notification.
- **M4-06 Send path and idempotency.** The signer reads nonce and block hash from `view_access_key` (finality final), builds a one-Transfer transaction from the treasury implicit account, has OpenBao sign the hash, verifies the signature locally, and stores `tx_hash` and the signed bytes before broadcasting (`send_tx`, `EXECUTED_OPTIMISTIC`). A retry first probes the stored hash. If it's unknown or still pending, it resubmits the same bytes (same nonce, so a transfer can never land twice). It only re-signs when NEAR reports the old transaction expired.
- **M4-07 NEAR `tx` wait modes.** Found on real testnet: querying an unknown transaction with a waiting `wait_until` blocks until the node's timeout (about 10–30 s) and returns TIMEOUT_ERROR. Probes use `wait_until: NONE`, which answers `UNKNOWN_TRANSACTION` immediately. Finalization uses `FINAL`.
- **M4-08 Retries and alerts.** Retryable errors (network, timeouts, 5xx, RPC TIMEOUT/INTERNAL) back off by `30 s × 2^(attempt−1)`, capped at one day, for 5 attempts. After the final attempt, or on a permanent error such as an on-chain failure, the payout stays `failed`, its cap reservation is released (no money moved), and the owner gets a `payout_failed` alert. Sealed or unreachable OpenBao pauses instead and does not count as an attempt.
- **M4-09 Statuses.** Added `blocked` (a gate failed: no verified address and/or no tax form), with a reason that names the missing gate(s). Blocked payouts reserve nothing. A payroll re-run updates the same blocked record, and creates the real payout once the gates pass. One live payout per worker per period (unique index; blocked excluded).
- **M4-10 Gates.** Address verification: ForeMan issues a challenge message (30-minute TTL, single use); the worker signs it with ed25519. For implicit accounts the key must equal the account; for named accounts the key must also be a full-access key on chain (`view_access_key`). Tax forms (W-9 / W-8BEN) are recorded from DocuSeal via `ContractService::fetch_tax_form`. Both gates are checked at payroll and again by the signer.
- **M4-11 Amounts.** NEAR amount = USD / (USD per NEAR), rounded to 6 decimal places of NEAR, stored as yocto in `NUMERIC(40,0)` (bound as text, since Decimal has only 28 digits). Rate, price time, network, and period are stored on the payout. The fee estimate is `0.001 NEAR × price` (a NEAR transfer costs about 0.0000446 NEAR, so this is conservative) and counts toward the cap. If there is no price, no NEAR amount is set and the payout cannot be approved; the binary skips payroll for that hour.
- **M4-12 Payroll.** Weekly periods (Monday 00:00 UTC). Owed = completed tasks in `[start, end)` × rate (task pay) or hours on completed tasks × rate (hourly pay), rounded to cents. Fired workers are still paid for completed work. The binary runs payroll hourly for the last complete week (idempotent), and expires pending approvals every 15 s.
- **M4-13 Approval API.** `POST /payouts/{id}/approve`, `POST /payouts/{id}/reject`, `GET /payouts/pending` in axom-api. Bearer = Supabase access token verified with HS256 and `SUPABASE_JWT_SECRET` (audience `authenticated`, expiry checked). MFA = `aal == "aal2"`. The admin must be an active row in `axom.admins`. 401 without a valid token, 403 for aal1 or non-admins, 409 for an invalid state. Projects on Supabase's newer asymmetric JWT keys need a JWKS verifier (TODO for milestone 7). No approval path exists in MCP or agent code.
- **M4-14 Signer service.** `axom-signer` binary: a loop every 10 s (process due, then finalize sent), `GET /health`, and `GET /treasury` (network, implicit account, public key). Testnet unless `NEAR_NETWORK=mainnet`, and mainnet additionally requires `AXOM_LIVE=true` and an explicit `NEAR_RPC_URL`. It talks to ForeMan only through the database (payout rows plus authorizations), never via axom-core/axom-hr calls into OpenBao.
- **M4-15 Crate notes.** `PriceQuote` moved to `axom_core::decision`. NEAR primitives (keys, implicit accounts, Borsh transfer encoding, yocto math) live in `axom_core::near` without the NEAR SDK. The NEAR JSON-RPC client and price feed are in axom-tools (`near_rpc`, `price`) with mocks. Price feed: `NEAR_PRICE_FEED_URL` plus a JSON pointer (`NEAR_PRICE_FEED_POINTER`), defaulting to CoinGecko.
- **M4-16 Opt-in tests.** `cargo test --workspace` runs everything that needs only Postgres. Real-OpenBao tests: `AXOM_TEST_BAO_BIN=/path/to/bao cargo test -p axom-signer -- --ignored --skip testnet_payout`. The live payout test needs a funded treasury (see M4-00): `OPENBAO_ADDR=... OPENBAO_TOKEN=... cargo test -p axom-signer --test testnet_live -- --ignored testnet_payout`.

## Milestone 5

- **M5-01 Adapter rules.** Every adapter in `axom_tools::adapters` is dry-run by default: the request is recorded with secrets redacted, and nothing leaves the process. `AXOM_LIVE=true` turns on real calls. Each method requires an `Authorized` value (which only an allow decision can create) whose action is one the adapter serves (for example DocuSeal accepts `send_contract`/`hire`; SMTP accepts `notify_owner`/`send_external_message`/`send_summary`); any other action gets `NotAuthorized`. Vendor errors map to Retryable (network, 408, 5xx), RateLimited (429, honoring Retry-After), NotAuthorized (401/403), and Permanent (other 4xx). Credentials come from the environment, and every error string passes through a redactor holding the adapter's secrets. Debug output never prints them.
- **M5-02 Vendor docs not verified (mismatch log).** The build environment could not reach docuseal.com, docs.postiz.com, twenty.com, warmbly.com, or opendesk.eu (all blocked by the network policy). The adapters follow the APIs as documented to the best of our knowledge, each marked UNVERIFIED in its module docs. To verify, allow those hosts and check each module header against the docs. Endpoint details sit in one place per adapter, so fixes are local.
- **M5-03 DocuSeal.** Base `<DOCUSEAL_URL>/api`, header `X-Auth-Token`. Create = `POST /submissions` with `send_email:false`. Send = `PUT /submitters/{id}` `{send_email:true}` for each submitter, because DocuSeal has no separate send call. This mismatch with the trait's create/send split is handled in the adapter. Status = `GET /submissions/{id}`. ## Milestone 6

- **M6-01 LiveKit tokens.** LiveKit has no official Rust server SDK we could pin, so `adapters::livekit` mints LiveKit's documented access-token JWT (HS256 with the API secret; `iss` = API key; `sub` = identity; `video` grants). Participant tokens last 15 minutes and carry only `roomJoin`, publish, subscribe, and data for one room, never `roomCreate` or admin. Server calls use a 60-second token with `roomCreate`/`roomAdmin`/`agent` grants against LiveKit's Twirp API (`RoomService/CreateRoom`, `/DeleteRoom`, `AgentDispatchService/CreateDispatch`). Dry-run by default, like every adapter.
- **M6-02 Infrastructure.** Self-hosted LiveKit with TURN on Coolify (dev and prod instances); the server config ships in milestone 9 (`infra/`). The agent is dispatched explicitly by name (`axom-interviewer`), with the job in the dispatch metadata: meeting id, instructions, questions, rubric, disclosure text, callback URL, and a per-meeting callback token.
- **M6-03 Meetings backend** (`axom_hr::meetings`, table `axom.meetings`):
  - `create_meeting` creates the room and one join token per invitee (only hashes are stored; a link opens 10 minutes before the start and expires 10 minutes after it, and is invalid once the meeting ends).
  - `POST /meetings/join` exchanges a join token for a LiveKit participant token.
  - `dispatch_agent` validates the questions and refuses rubric criteria that name protected characteristics (age, gender, race, nationality, religion, disability, family, orientation, accent, appearance, and similar). It stores the rubric with the meeting.
  - The agent is sent into the room only once the join window opens (10 minutes before the start): right away if `dispatch_agent` is called inside the window, otherwise by the first `POST /meetings/join` inside it (`meetings::send_agent`, once per meeting, claimed atomically). The room is recreated first. Found live: interviews are booked a day ahead, and dispatching at booking time meant the agent joined an empty room that LiveKit closed after its 10-minute empty timeout, taking the dispatch with it, so the candidate arrived in a fresh room with no interviewer. The callback token is minted at send time (its hash stored before the dispatch). A send failure is audited (`meeting.agent_sent`/`failed`) and does not block the participant; the next join retries. An admin host link used before the window does not bring the agent.
  - The agent's callback base (consent, results, and the company's interview keys) is `AXOM_AGENT_CALLBACK_URL`, falling back to `AXOM_PUBLIC_API_URL`. Found live: in Docker Compose the public `http://localhost:8080` is the agent's own container, so it could not report back or fetch keys; Compose now sets `http://axom:8080`. The public URL still goes in links people see.
  - `POST /meetings/{id}/callback` (per-meeting bearer token): consent must arrive first, and a transcript without recorded consent is rejected. A decline closes the meeting. Scores must be integers 1–5 on rubric criteria only.
- **M6-04 Providers.** Voice: Deepgram alone, for both speech-to-text and text-to-speech (Aura), with one key (`DEEPGRAM_API_KEY`; optional `AXOM_MEET_TTS_VOICE`, `AXOM_MEET_STT_MODEL`). Cartesia is optional: `AXOM_MEET_TTS=cartesia` with `CARTESIA_API_KEY`, installed as the `cartesia` extra (`EXTRAS=cartesia` Docker build arg); a Cartesia key alone does not switch providers. LLM: Anthropic Claude (`ANTHROPIC_API_KEY`, `AXOM_MEET_LLM_MODEL`, default `claude-sonnet-5-5`). VAD: Silero (local). Built on LiveKit Agents 1.8.11. All are swappable in `meet-agent/axom_meet/agent.py`.
- **M6-05 Agent design.** Every spoken line comes from a deterministic state machine (`axom_meet/interview.py`): disclosure, then consent, then questions, then closing. `on_user_turn_completed` feeds each finished turn to it and raises `StopResponse`, so the session LLM never speaks on its own. The LLM only proposes one follow-up per question; `guards.safe_follow_up` drops anything that isn't a single short question, mentions pay or terms, or makes a commitment. Any participant mention of pay, rates, offers, contracts, or terms gets a fixed refusal and the same question repeated. Consent parsing is deterministic: a negative anywhere means declined; hedges and questions ("not sure", "maybe", "?") are unclear; one re-ask, then a second unclear answer counts as declined. Found by test: "I'm not sure" was being read as yes.
- **M6-06 Results and injection.** The transcript goes to the LLM only inside an untrusted block. The result object can hold only `summary` and `scores` (scores filtered to rubric criteria, integers 1–5). The callback client sends only whitelisted fields, so no recipient or action can come out of the agent. The agent never emails anyone. `send_summary` recipients come from the caller (dashboard or MCP) and must be invitees, the owner, or recipients the owner added in the dashboard (MFA admin), enforced by the policy engine's `SendExternalMessage` check. Each summary is also saved as a CRM note on the candidate.
- **M6-07 Participant UI.** `meet-web`: Vite and React with `@livekit/components-react` (versions pinned at least two weeks old). Join by link (`/join?t=<token>`); `VideoConference` provides camera and mic controls and room chat. A banner says the meeting includes an AI interviewer. The API now sends CORS headers for `AXOM_CORS_ORIGINS`.
- **M6-09 Timed interviews, link expiry, reminders** (migration `20261114000007_meeting_timing.sql`).
  - Interviews last 10 minutes (`meetings::INTERVIEW_MINUTES`, stored as `duration_minutes`). The agent gets `max_duration_secs` in its dispatch metadata; the clock starts with the disclosure. In the last minute no new question or follow-up is asked, so the next answer closes the interview; at the limit the agent interrupts, says a closing line, posts results (if consent was given), and leaves. The participant page shows a countdown.
  - Join links open 10 minutes before the start and expire 10 minutes after it (`join_window`). Too-early and expired links get a clear message with the time. Meetings can't be created once that window has passed, and the agent leaves if nobody joins by the link deadline (`join_deadline` in metadata).
  - `expire_meetings` (background loop, every 15 s) marks meetings still scheduled or dispatched 30 minutes after the start (link expiry + limit + 10 min grace) as `expired`, closes the LiveKit room, audits, and notifies the owner.
  - `send_due_reminders` (same loop) reminds invitees 24 hours, 1 hour, and 10 minutes before the start. Each slot goes out once per meeting (`axom.meeting_reminders`); slots that had passed when the meeting was booked are skipped. Raw invite tokens aren't stored, so each reminder mints a fresh join link with the same expiry. Email reminders carry an ICS invite with alarms 1 hour and 10 minutes before; Upwork applicants without a shared email are reminded on Upwork. Every send passes the policy engine's `SendExternalMessage` check against the invitee list.
  - Privacy: reminder rows keep only a count, audit entries use email pseudonyms, the expiry notification leaves out the title (it can name the candidate), and erased invitees are skipped. Join links an admin opens from the dashboard are host links (`meeting_invites.host`): they work before the candidate's window opens.
  - Voice keys come through the company's keys first, then the agent's environment, like the other providers.
- **M6-10 Day-long links, 15-minute interviews, agent on first join** (migration `20261114000014_meeting_first_join.sql`; supersedes the 10-minute numbers in M6-09).
  - Interviews last 15 minutes. Join links still open 10 minutes before the start but now expire 24 hours after it (`JOIN_LATE_MINUTES`), so a candidate can join any time that day.
  - The first invitee join records `meetings.first_joined_at` (audited as `meeting.first_join`, pseudonymous). From then on every invitee link for the meeting, reminder links included, stops working once the interview's time limit has passed since that join; a late first join still gets the full 15 minutes. Admin host links are not affected.
  - The agent is sent only when an invitee joins inside the window (or by `dispatch_agent` if one already has), never just because the window is open: with a day-long window the agent would otherwise sit in an empty room that LiveKit closes after 10 minutes.
  - The hiring pipeline books interviews 5 minutes after the invite (`INTERVIEW_DELAY_MINUTES`) instead of a day ahead, and the invite message gives the link's hours and the 15-minute limit. A no-show is declared only after the link has expired plus a late joiner's limit and grace (`interview_no_show_after`), and also covers meetings the sweep already marked expired, so an interview in progress is never cancelled.
- **M6-11 The interview starts when the applicant joins.** Invitee links no longer open 10 minutes before the scheduled time: they work from the moment they are sent until 24 hours after it (`link_expiry`), and an invitee's join sends the assigned agent in right away, whatever the scheduled time. Found live: an interview booked for the next day showed a host-joined room with no agent and no captions (captions are the agent's LiveKit transcriptions). An admin host link still never brings the agent; the 15-minute clock still starts at the first invitee join.
- **M6-12 A failed invite reuses its meeting.** Found live: with SMTP rejecting its credentials, every hiring pass booked a new meeting and room for the same shortlisted candidate. `invite_to_interview` now links the meeting to the candidate before sending. A failed send is audited (`hiring.invite`/`send_failed`, with the error) and leaves the candidate shortlisted; the next pass sends a fresh link (`meetings::new_invite_link`) for the same meeting while it is unjoined with at least an hour of link time left, and otherwise cancels it and books a new one. If the candidate already joined it (the send errored but the link arrived), they are marked invited and nothing is cancelled.
- **M6-13 No join link without interviewer questions.** The agent is only sent to a meeting with questions, but the dashboard and the MCP `create_meeting` tool emailed join links at creation while questions were a separate, optional step, so an applicant could open a room the agent would never join. `send_invites` and the reminder sweep now call `meetings::ensure_interviewer` first, which stores default instructions, `default_questions()` and `default_rubric()` on a meeting that has none (audited as `meeting.dispatch_agent`/`defaulted`); questions someone set are never overwritten. `dispatch_agent` may replace the job (defaults included) until the agent is in the room, and the dashboard shows "Edit questions" until then.
- **M6-08 Not run live.** No LiveKit server, STT, TTS, or LLM keys are available in the build environment, so the agent was not run in a real room. The agent module imports against the real SDK; the interview logic, guards, and callback are tested with a fake participant (9 Python tests); the backend flow is tested in Rust (5 tests).

- **M8-02 Human hiring flow** (`axom_hr::hiring`), every step audited:
  1. `post_job`: HR writes the job spec from the planned human role (title, required skills, rate, KPIs).   5. `send_contract`: requires `interviewed` status and a rubric mean of at least 3.5. The policy `SendContract` check means owner-approved templates only; only field values (name, role, rate) are filled, and no contract text is written.   6. `complete_hire`: when DocuSeal reports the submission completed, the worker becomes active and the job posting and hiring request are filled. A declined contract marks the candidate declined and the worker record fired (terminal).

## Post-milestone review: spec gaps closed

- **R-01 Hiring runs on its own.** `hiring::advance_hiring` (hourly, after `process_open_requests`) moves each open posting one step per pass: shortlist up to 3, invite them to the AI interview, score finished interviews, send the contract to the best candidate at or above 3.5 (one at a time), and activate the hire once DocuSeal reports it signed. On hire it rejects the remaining candidates and sends the freelancer their task-intake token over Upwork. Each step acts only on candidates in the matching state, so repeated runs are safe.
- **R-02 Meeting invites.** Creating a meeting from the dashboard or MCP emails each invitee their own join link with an ICS calendar invite, through the SMTP adapter, under a `SendExternalMessage` policy check limited to that meeting's invitees. Placeholder addresses (`*.invalid`) are skipped; those candidates get the link over Upwork.
- **R-03 Candidate data retention and deletion.** `[privacy] candidate_retention_days` (180) in `config/policy.toml`. Hourly, data of non-hired candidates past retention is redacted: name, email, skills, cover letter, transcript, summary, invitee addresses, consent wording, and join links. Rubric, scores, and the consent flag stay without identity, for bias audits. An MFA admin can delete a candidate's data on request (`POST /admin/candidates/{id}/delete`). For hired freelancers and contracts that request is refused (payroll and tax records), to be handled manually with legal advice. Because the audit log is append-only, it now stores only pseudonyms (`email:<sha256 prefix>`) for invitees and recipients, and only the consent flag and time; a test scans it for personal data.
- **R-04 Tax forms.** `gates::sync_missing_tax_forms` (hourly) asks DocuSeal for completed W-9/W-8BEN submissions of active freelancers who have none on file, matched by the email they applied with.
- **R-05 Supabase signing keys.** `axom-api/src/auth.rs` verifies tokens against the project's JWKS (`SUPABASE_JWKS_URL`): ES256 or RS256, chosen by `kid`, cached, and refreshed at most once a minute when an unknown `kid` appears. The legacy HS256 secret works alongside it during a migration. The algorithm comes from the verifying key, so an HS256 token can never be checked against a public key, and symmetric keys are never accepted from a JWKS. Tested with a real P-256 key pair: algorithm confusion, an unknown key, expiry, and a JWKS outage are all rejected.
- **R-06 Price feed key.** `NEAR_PRICE_FEED_API_KEY` is sent in `NEAR_PRICE_FEED_API_KEY_HEADER` (default `x-cg-demo-api-key`). CoinGecko returned 403 to unauthenticated calls during testing.
- **R-07 CI.** `.github/workflows/ci.yml` runs on pushes to `main` and on pull requests: clippy with warnings as errors, the Rust workspace tests against a Postgres 16 service (including the end-to-end run, which needs Python), the meeting-agent tests (pytest only), and both web builds. Not yet run on GitHub. A newer stable Rust could add lints that fail `-D warnings`; pin the toolchain if that becomes noisy.
- **R-08 Branch.** Development moved to `main` at the human's request. `main` was created from the original development branch, which is being retired. The repository's default branch on GitHub is still the old branch until changed in the repo settings.

## ForeMan Jobs (own jobs board)

- **J-01 Why.** Upwork's User Agreement (section 7) treats paying a freelancer met on Upwork outside Upwork as circumvention unless a conversion fee is paid, and Upwork has no crypto payouts. Paying Upwork hires in NEAR would break that. ForeMan therefore has its own public board and uses it by default (`AXOM_MARKETPLACE=board`). Owner's legal review should confirm the Upwork reading before live mode.
- **J-02 Same pipeline.** `axom_hr::board::AxomBoard` implements `FreelanceMarketplace`, so posting (after the policy check), shortlisting, AI interviews, contracts, and activation are unchanged. Jobs live in `axom.board_jobs`, applications in `axom.board_applications`. Applicants are contacted by email through the SMTP adapter, under the same `send_external_message` policy decision. Each posting records its `marketplace`, and `advance_hiring` only advances postings of the marketplace in use (found in the preview: an older Upwork posting failed when advanced through the board).
- **J-03 Upwork hires are never paid in NEAR.** New payout gate `GateBlock::HiredViaUpwork`: a worker hired from an Upwork posting is blocked from NEAR payouts, alongside the address and tax-form gates.
- **J-04 Public endpoints.** `GET /jobs`, `GET /jobs/{id}`, `POST /jobs/{id}/apply`, with no sign-in. Applications are validated (name, email, up to 20 normalised skill tags, note up to 5000 characters, http(s) portfolio link), require accepting the privacy notice, are unique per email per job, capped at 500 per job (checked under a row lock), and limited to 30 per minute across the API. Everything submitted is untrusted data: matched deterministically, never interpreted. A per-IP limit needs the reverse proxy's client IP; add it at the proxy (Coolify/Traefik rate-limit middleware) when deploying.
- **J-05 Privacy.** Redacting a candidate also redacts their board application. Applications that never became candidates are deleted after the retention period. The privacy notice on the apply form states 180 days; update it if `[privacy] candidate_retention_days` changes.
- **J-06 Board jobs close** once their posting is filled (`board::close_finished_jobs`, hourly), so filled roles leave the public board and stop taking applications.
- **J-07 Site.** The board is part of `meet-web` (`/jobs`, `/jobs/<id>`), the candidate-facing site; its Vite config proxies `/api` to the API for single-port previews, like the dashboard.
- **J-08 AI workers can ask for a hire.** An owner task like "hire a copywriter" used to reach an AI worker that had no way into hiring, and it finished with nothing done. Thinking workers now always get a `request_hire` tool (like `ask_owner`) that only opens a `human_freelancer` hiring request for the task, with the worker's job title (`hiring_requests.title`, used by `post_job`) and normalised skills. Everything after that is the existing pipeline: policy check with the approved contract template, posting on the configured marketplace, shortlist, AI interview, contract. Guardrails: freelancers only (never a new AI worker with tools), one open request per task (the existing unique index), title and skills trimmed and capped. This puts it in the same place as routing, which already opens requests on its own. The worker's prompt still says it can't make offers, approve payments, or fire.
- **J-09 Job text, the owner's rate, and fewer skills.** The first live run posted a bare title with eight skills, and the worker had to tuck the owner's $25 budget into the reason. `request_hire` now takes an optional `description` (plain text, up to 3000 characters, shown on the public job page under "About the role" and sent to Upwork ahead of the KPIs) and an optional `rate_usd` (`hiring_requests.description`, `rate_usd`, `board_jobs.description`; migration 13). A rate must be positive and at most the payout approval threshold (`[payouts] approval_threshold_usd`, $50 now); a higher one is refused and the worker is told to leave it out, so the planned role's rate (or $25) is posted. Skills are limited to 5, because the shortlist scores applicants by the share of the job's skills they list and long lists of niche tags push every score down. The tool's description and result now say that posting needs no further approval and the owner is told when the contract goes out (the worker had assumed every step needed approval).

## Multi-tenant platform (anyone can sign up companies)

Asked for: a customised dashboard, multi-tenancy with open sign-up, subscriptions paid in NEAR, companies connecting their own tools and API keys, and Google's design system. Choices confirmed with the owner: each company has its own treasury (no pooled customer funds), one plan with a free trial, NEAR testnet for now, Material UI.

- **MT-01 A database per company.** `AXOM_MULTI_TENANT=true` makes `DATABASE_URL` the platform database (`supabase/platform_migrations`: companies, members, invites, encrypted keys, invoices, an append-only platform audit log). Signing up a company runs `CREATE DATABASE axom_t_<id>` on the same server and applies the normal migrations, so every existing HR, payout, and hiring query runs unchanged, and a forgotten `WHERE` can't leak one company's rows to another. Alternatives considered: a `tenant_id` column with row-level security (hundreds of queries to change, and the app connects as table owner, which bypasses RLS unless forced) and schema-per-company (every query is `axom.`-qualified). Cost: one small lazy pool per active company (max 4 connections, idle-closed after 10 minutes). The database role needs `CREATEDB`; database names come from UUID hex only.
- **MT-02 Routing.** `/platform/...` is the control plane. `/t/<company>/...` strips the prefix and hands the request to that company's own `axom_api` router (built with its pool, its adapters, and its MCP token; cached 5 minutes and rebuilt on key changes). Admin checks inside a company use that company's `axom.admins`, which the platform keeps in step with membership. Found while testing: the read-only views a single company serves without sign-in (org chart, tasks, cap, notifications, spot checks) would expose every company's data on a shared platform, so on the platform they need a signed-in, MFA-verified member of that company. `axom_api::routes()` is the router without CORS, so CORS is applied once.
- **MT-03 Sign-up and members.** Anyone with a Supabase account can sign up; creating a company needs an `aal2` session (TOTP). The creator becomes owner and first admin. Owners invite by email; an invite is accepted when an MFA-verified user with that email opens the dashboard. That relies on Supabase confirming email addresses: turn on "Confirm email" in production (docs/SETUP.md). One person can own at most 5 companies (blunts trial abuse). Owners can remove admins (who lose access immediately) but not themselves.
- **MT-04 Integration keys.** Stored in `platform.secrets`, encrypted with AES-256-GCM under `AXOM_SECRETS_KEY`, a fresh nonce per value, and the company id plus key name as associated data, so a ciphertext copied to another company or key fails to decrypt (tested). Only names in a fixed catalog can be stored; secret values are never returned (hint: last four characters); the audit log records which key changed, never its value (tested). Adapters gained `from_config(&dyn ConfigSource)`; a company's keys come first, with the platform's environment as fallback only for shared services (SMTP, LiveKit), never for vendor accounts like DocuSeal or Upwork.
- **MT-05 Subscriptions in NEAR.** One plan (`AXOM_PLAN_PRICE_USD`, default 49) with a free trial (`AXOM_TRIAL_DAYS`, default 14). An invoice converts the USD price at the live NEAR price (refused if the quote is older than 10 minutes) and is payable to `AXOM_BILLING_ACCOUNT` for 24 hours; opening a new invoice expires older open ones. The customer sends NEAR from any wallet and submits the transaction hash and sending account. ForeMan fetches the transaction from NEAR RPC and checks: success, final, receiver, signer, deposit exactly the invoice amount (each invoice asks for its own amount: the price rounded up to 0.01 NEAR plus six random digits in decimal places 3 to 8, unique among invoices still payable, because a NEAR transfer has no memo and the amount is what ties a payment to one invoice), block time after the invoice was opened and within its window, and that the hash hasn't paid another invoice (unique index, plus a check inside the paying transaction). Paying extends from the later of now, the current paid-until date, or the trial end. Verified against real testnet: a real earlier payout transaction was found and refused for the wrong receiver. An expired subscription stops the company's background jobs and pauses new job applications; the dashboard stays available. No wallet connection in the browser yet (a NEAR wallet-selector integration would remove the copy-paste step).
- **MT-06 A treasury per company.** A key `axom-treasury-<id>` in OpenBao: ed25519, not exportable, no plaintext backup, deletion not allowed. The platform holds a provisioner token (`infra/openbao/axom-provisioner.hcl`) that can create and lock those keys and nothing else; the signer's policy gains sign and read on `axom-treasury-*`. Checked on OpenBao 2.7.1: the provisioner gets 200 creating a company key and 403 for sign, export, delete, and the single-company `axom-treasury` key. The company funds its own implicit account, so ForeMan never holds customer money. Approval and attestation keys stay platform-wide; payout ids are random UUIDs checked against the row in the company's own database, so an authorization can't be replayed into another company.
- **MT-07 Background jobs per company.** The single-company loop moved into `axom_app::runtime::Runtime`. On the platform a supervisor checks every minute: it runs one runtime per company with a current trial or subscription, restarts it when the company's keys change, and stops it when the subscription lapses. The multi-tenant signer lists companies with a treasury every 10 seconds and processes each with its own key; one company's failure doesn't block another's.
- **MT-08 Plans for new companies.** `POST /platform/companies/<c>/plan` takes a goal, budget, deadline, and objectives (validated), runs the existing planner, and routes tasks. Only the first plan is accepted (replacing a plan stays a deliberate admin action, as before).
- **MT-09 Dashboard.** Rebuilt with Material UI 9.5 (Google's Material Design): Roboto, Google blue, light and dark themes, a navigation drawer that becomes a menu on phones. New: account creation and password reset, a three-step company setup, a company switcher, Integrations, Billing (a three-step NEAR payment), Members, and Settings (plan, treasury, links, kill switch). Every earlier screen is kept (approvals, cap meter and change, meetings with dispatch and transcripts, firings now in Activity). In single-company mode the platform pages are hidden. The candidate site understands `/t/<company>/jobs` and `/t/<company>/join` links.
- **MT-10 Tested.** `axom-platform/tests/platform.rs`: separate databases and caps per company, slug rules, MFA required, HTTP routing and members-only views, key encryption and masking, invites and removal, treasury (owner only, idempotent), plans, and every payment check (wrong receiver, too little, failed, outside the window, wrong sender, reuse, bad hash). A browser run of the whole flow against a real platform server, real OpenBao, and a local price feed: sign-up, company, plan (2 departments, 2 AI workers), every page, saving keys, an invoice (14 NEAR for 49 USD at 3.5), a refused fake payment, treasury creation, an invite, dark mode, and a phone-width layout with no horizontal scroll. Single-company mode re-checked with the judge database.

## Admin-defined tools (MCP servers and webhooks)

Asked for: let admins create tools and MCP servers instead of only the hardcoded ones.

- **CT-01 What changed.** Each company's database has `axom.tool_servers` and `axom.custom_tools` (migration `20261109000001`). On the Tools page an MFA admin adds an MCP server (ForeMan runs `initialize`, keeps the `Mcp-Session-Id`, and pages through `tools/list`; JSON and event-stream answers are both read) or a webhook (one tool named after it). MCP tools are named `<server>.<tool>` and can be enabled or disabled one by one; refreshing adds new tools and removes vanished ones, taking them off every allowlist. Removing a server does the same.
- **CT-02 The built-ins stay.** DocuSeal, SMTP, Postiz, the CRM, Warmbly, Upwork, and LiveKit remain built in: hiring, contracts, tax forms, interviews, and notifications call them directly with typed operations, which a generic tool call can't replace safely. They also remain available as tool names for AI workers. New capabilities for AI workers come from admin-defined tools.
- **CT-03 Who can do what.** Adding, refreshing, enabling, and removing tools needs an MFA-verified admin and is audited (URLs and names; never tokens, tested). Giving tools to a worker is the existing protected `ChangeToolAllowlist` policy action (MFA admin only, before/after audited); only AI workers can have tools, and only tools that exist and are enabled. Every call is the existing `ExecuteTool` check against the worker's allowlist.
- **CT-04 Untrusted URLs.** Admins type the URLs, and on the platform they are other companies' admins, so each request goes through a URL guard: HTTPS only; the host must resolve to public addresses only (refused: loopback, RFC 1918, link-local including cloud metadata 169.254.169.254, carrier-grade NAT, multicast, reserved, IPv6 unique-local and link-local, IPv4-mapped and NAT64 forms of those); the connection is pinned to the checked address (no DNS-rebinding window); redirects are not followed; responses are capped at 2 MB; credentials in URLs are refused. `AXOM_TOOLS_ALLOW_PRIVATE=true` relaxes this for a single-company deployment reaching its own services; the platform always uses the strict guard. Checked live on the platform preview: plain http, 127.0.0.1, localhost, and 169.254.169.254 are all refused.
- **CT-05 Tokens.** The auth header value is encrypted (AES-256-GCM, `AXOM_SECRETS_KEY`, bound to the tool server's id); only a hint (last four characters) is returned. The encryption helper moved to `axom_core::secretbox` so single-company deployments use it too; without `AXOM_SECRETS_KEY`, tools without tokens still work and tools with tokens are refused with a clear message.
- **CT-06 Dry-run.** Tool calls follow `AXOM_LIVE`: in dry-run the exact call (tool, URL, arguments) is recorded as the task's output and nothing is sent. Discovering an MCP server's tools does contact it in dry-run: it is a read an admin starts, and the alternative (typing tool names by hand) is error-prone.
- **CT-07 Arguments.** Agents don't yet plan tool arguments with an LLM, so ForeMan fills string properties named like a request (`query`, `prompt`, `input`, `objective`, `text`, `question`, `instructions`, ...) with the task objective, and `task_id` with the task id. Tools needing other arguments will report an error, which fails the task visibly. A planning step that fills arguments from the schema is the natural next step.
- **CT-08 Tasks run continuously.** The company runtime now routes and runs tasks every minute (before: once at startup), so tasks added in the dashboard, including ones needing a custom tool, are picked up without a restart.
- **CT-09 Existing companies.** Platform company databases are now migrated when first opened after an upgrade, so new migrations (like this one) reach companies created earlier. Checked on the preview: an existing company got the tool tables on restart.
- **CT-10 Tested.** `axom-tools/tests/custom_mcp.rs` (fake MCP server: session, pagination, event stream, tool errors, wrong token, strict guard, webhook auth, redirect to cloud metadata refused), unit tests for address classification and stream parsing, and `axom-planner/tests/custom_tools.rs` (discovery, encrypted token, name rules, policy on allowlists, dry-run and live runs, blocked and disabled tools, clean-up on refresh and delete). A browser run: add an MCP server, its tools appear, give one to an AI worker, create a task needing it; the runtime ran it within a minute (dry-run output with the arguments it would send).

## Milestone 11: Cross-chain payouts (NEAR Intents)

Built 2026-11-14 during the NEAR HACKATHON window, on top of the existing payroll and signer.

- **XC-01 Shape.** Workers are paid on other chains through NEAR Intents (1Click API). The treasury, policy, cap, approvals, and signature all stay on NEAR: for a cross-chain payout the signer deposits the authorized wNEAR into a 1Click quote, and solvers deliver the destination asset. No bridge keys, no per-chain wallets, no new custody.
- **XC-02 Who names the destination.** Only the worker, by signing a challenge (chain, 1Click asset id, address, worker, NEAR account, nonce, 30-minute expiry) with the key of their already verified NEAR address. ForeMan never takes a destination from the agent, an admin, or an email. `payout_destinations` keeps one active row per worker and network; a new one revokes the old. Named NEAR accounts are re-checked on chain (the key must still be full access). Format checks per chain family (EVM hex, Solana base58/32 bytes, Bitcoin bech32/base58, Tron, NEAR) catch typos and wrong-chain addresses; they cannot prove ownership of the foreign address, which is the worker's own signed statement.
- **XC-03 Recipient stays the NEAR account.** `payouts.recipient` is still the worker's verified NEAR account, so the per-recipient 24 h window, the address gate, and the signer's verified-address check work unchanged. The destination (`destination_id`, `dest_chain`, `dest_asset`, `dest_address`) is fixed at creation. Payroll uses a destination only if it was signed by the NEAR address being paid; otherwise it pays in NEAR and logs a warning.
- **XC-04 Authorization covers the destination.** `PayoutAuthorization.destination` (optional, omitted from the signed JSON when absent, so NEAR-only authorizations and their signatures are byte-for-byte unchanged). Both automatic attestations and MFA approvals include it, so an admin approves the address on the other chain, not just an amount. The dashboard's approval dialog shows the destination address grouped in fours, the route, and the NEAR account that signed it.
- **XC-05 Amounts and fees.** `EXACT_INPUT`. The NEAR amount = (owed USD + route fee) / price, where route fee = `route_fee_bps` (default 100) of the payout; the worker receives about what they are owed. The route fee and the deposit's wNEAR storage (2 × 0.00125 NEAR, refunded when already registered) are added to `fee_usd` and count toward the cap. Measured on mainnet dry quotes (2026-11-14): 5 USD → 4.97 USDC on Base (~0.6%, 24 s); 50 USD → BTC (~2.8%, ~8 min). 1Click added a 20 bps app fee to keyless quotes.
- **XC-06 Quote checks (signer, before signing).** Quote requested at send time (not at approval, which may be days earlier) with `refundTo` = treasury implicit account, `refundType: ORIGIN_CHAIN`, slippage `slippage_bps`. Refused, never retried, if the echoed `quoteRequest` differs in recipient, destination asset, origin asset, refund account, or amount; if `amountIn` differs; if there is no deposit address or it is not a NEAR account (or is the treasury); or if a deposit memo is required. Retried later (backoff, then final failure releases the cap and alerts) if the deadline is under 5 minutes away, the USD output is missing, or it is more than `max_shortfall_bps` (default 300) below the owed amount. The full quote and 1Click's signature are stored on the payout, as 1Click asks integrators to do for disputes. Verified on mainnet that 1Click echoes the request exactly, including address case.
- **XC-07 The deposit transaction.** One transaction to the wNEAR contract (`wrap.near` / `wrap.testnet`), atomic in one receipt: `storage_deposit` for the treasury (so `near_deposit` never deducts a registration fee from the amount), `storage_deposit` for the deposit address, `near_deposit` of exactly the authorized yocto, `ft_transfer` of exactly that amount (1 yocto attached, memo `axom payout <id>`), 15 Tgas each. The signer builds it from a template and checks it against the template before asking OpenBao to sign. 1Click's docs say only "transfer tokens to the depositAddress" for `ORIGIN_CHAIN` and do not say whether native NEAR is accepted for `nep141:wrap.near`; an `ft_transfer` of the NEP-141 token is the unambiguous reading.
- **XC-08 Borsh FunctionCall.** `axom_core::near` now encodes Transfer and FunctionCall actions (tag 2: method string, args bytes, gas u64, deposit u128) and decodes both. Golden vector for the full deposit transaction produced independently with near-js (`@near-js/transactions` 1.3.3 `encodeTransaction`), matched byte for byte. The existing near-api-py transfer vector still passes.
- **XC-09 Idempotency and retries.** Unchanged from M4-06: signed bytes are stored before broadcast and resubmitted on unknown outcomes. If NEAR reports the stored transaction expired, the quote is dropped with it and the next attempt gets a fresh deposit address (nothing reached the old one).
- **XC-10 Finalization.** `sent` = the NEAR deposit executed (cap committed). `finalized` only after the NEAR transaction is final and 1Click reports `SUCCESS`; destination-chain hashes are stored. `REFUNDED` → new terminal status `refunded` with a `payout_refunded` owner alert; the deposit comes back to the treasury as wNEAR (unwrap with `near_withdraw`). The cap stays committed for a refunded payout (conservative: the cap is a spend ceiling; an admin can raise it). `FAILED` and `INCOMPLETE_DEPOSIT` keep the payout `sent` and alert the owner once per status change.
- **XC-11 Testnet.** NEAR Intents has no testnet (hackathon Q-007). The signer's intents client is `1click` on mainnet and `simulated` on testnet (`AXOM_INTENTS` overrides; `1click` on testnet and `simulated` on mainnet are refused at start-up). The simulator quotes like a fair solver (input USD minus 30 bps), issues a fresh implicit-account deposit address per quote, and reports `SUCCESS` with a `simulated-…` destination hash. The NEAR leg (the wNEAR deposit) is a real testnet transaction. Judge mode also prints a real mainnet `dry: true` quote for the same route. `axom intents-quote` and `axom intents-tokens` query 1Click directly. 1Click returns HTTP 400 "Internal server error" when `refundTo` is a contract such as `wrap.near`; dry quotes use a plain implicit account.
- **XC-12 Not verified.** The judge-mode testnet run could not fund its treasury: the testnet helper (faucet) returned HTTP 429 on 2026-11-14, so the wNEAR deposit transaction has not yet been accepted by a real node. Its encoding matches near-js byte for byte (XC-08) and the signer path runs against the node-like mock; the first `./judge/run.sh` with faucet access (or `JUDGE_COLD_ACCOUNT`/`JUDGE_COLD_KEY_FILE`) will submit it to `wrap.testnet` and print the link. No mainnet deposit was made either (it would move real funds; needs the owner's go-ahead, `AXOM_LIVE=true`, and legal review). So 1Click's handling of an `ft_transfer` deposit from ForeMan's exact transaction, and its status transitions for it, are unverified end to end on mainnet. Recommended first live step: one payout of a few USD to a team-controlled address, watched in the 1Click explorer.
- **XC-13 API and UI.** Worker endpoints `GET/DELETE /workers/me/payout-destination`, `POST …/challenge`, `POST …/verify` (worker token; a challenge can only be verified by the worker it was issued to). ## Milestone 12: Treasury yield on Rhea Finance lending

Built 2026-11-14 during the NEAR HACKATHON window (Rhea is a partner; tracks: Autonomous Business, AI Security).

- **RY-01 Use case.** The treasury holds payroll money that sits idle most of the month. Payroll can't spend more than the monthly cap allows, so everything above "what the cap still allows this month" is safe to put to work. That surplus is supplied to Rhea lending and comes back before payroll needs it. It reuses ForeMan's existing controls (cap, policy engine, kill switch, OpenBao signer, audit log) rather than adding new trust.
- **RY-02 Asset: wNEAR.** Payouts are in NEAR, so supplying wNEAR needs no swaps and no price exposure beyond what the treasury already has. Live rates on 2026-11-14 (`get_assets_paged_detailed`): wNEAR 0.32% supply APR, native USDC 10.80%, USDt 8.73%. A USDC treasury (no NEAR price risk against USD payroll, ~10% yield) is the natural next step, but needs a swap leg (Rhea DEX or the smart router) and USDC payouts; not built.
- **RY-03 The rule (`axom_hr::treasury::plan`, pure).** Floor = yocto owed on unsent payouts (`pending_approval`, `approved`, `failed` with a retry scheduled) + the cap's remaining USD this month at the current price + `min_liquid_near`. Target = floor × (1 + `liquidity_margin_pct`). Order: unwrap any wNEAR the treasury holds (≥ 0.001); refuse if Rhea reports `extra_decimals` ≠ 0; yield off and something supplied → withdraw all; liquid < floor → withdraw up to the target (at least `min_move_near`, at most what is supplied); yield on, fresh price, deposits open → supply min(liquid − target − 0.05 NEAR gas reserve, room under `max_deployed_pct`), rounded down to 0.001 NEAR, if ≥ `min_move_near`, registering first if needed. Without a fresh price (policy `price_max_age_secs`), the floor counts only payouts already owed: no supply, but withdrawals still cover what is owed. The gap between floor and target is hysteresis, so small payouts don't cause churn.
- **RY-04 Templates (`axom_core::rhea`).** Register: `storage_deposit {}` on the lending contract with the contract's reported minimum (0.1 NEAR; refused above 0.25). Supply: one transaction to wNEAR with `storage_deposit {registration_only}`, `near_deposit`, `ft_transfer_call {receiver_id: lending, amount, msg: ""}` (1 yocto, 100 Tgas). Withdraw: `execute {actions:[{Withdraw:{token_id, max_amount}}]}` on the lending contract (1 yocto, 150 Tgas). Unwrap: `near_withdraw` on wNEAR. `check_tx` compares the built transaction against the template and the treasury account; tests assert no template names any receiver but the lending contract, and none contains `Borrow`, `IncreaseCollateral`, or `account_id`.
- **RY-05 Verified against mainnet.** Rhea's SDK docs don't give raw contract calls (their samples are placeholders), so each call was checked on chain (2026-11-14): `get_config` (Pyth oracle, `priceoracle.near` disabled), `storage_balance_bounds` = 0.1 NEAR, `get_asset("wrap.near")` with `extra_decimals: 0`, `get_account` shape (`supplied[]` with `token_id`, `balance`), `storage_balance_of` = `null` for unregistered accounts. Live transactions on NearBlocks show plain supplies arriving as `ft_on_transfer {"msg": ""}` and accounts withdrawing wNEAR with `execute {"actions":[{"Withdraw":{"token_id":"wrap.near"}}]}` and 1 yocto, without an oracle call, paid back by `ft_transfer` (e.g. tx `2sEW3oMPbM3Y…`, status success). Testnet deployment: `contract.1689937928.burrow.testnet` (lists `wrap.testnet`, same views); `contract.1638481328.burrow.testnet` is an older one. `examples/rhea_position.rs` reads any account's position from live RPC.
- **RY-06 Policy.** New `Action::TreasuryMove {kind, amount_near}`: allowed only for `Actor::System` (the planner), never an LLM agent or a person; `supply`/`register` only with `yield_enabled`; `withdraw`/`unwrap` always (money coming home); denied under the kill switch like everything else. `[treasury]` in `config/policy.toml` (off by default; `TREASURY_YIELD_ENABLED=true` overrides). Company rules (stricter only) apply as for payouts.
- **RY-07 Signer.** `Signer::manage_treasury`, called about once a minute per company, only in a tick that sent no payouts (one nonce in flight at a time). One move per call. Moves are stored (`axom.treasury_moves`) with the signed bytes before broadcast; an unknown outcome blocks new moves, is probed, and after 60 s the same bytes are resubmitted (never re-signed); `Expired`/`InvalidNonce` marks it failed and the planner re-reads the chain. Failed moves alert the owner (`treasury_move_failed`). A sealed OpenBao pauses. The planner's latest view goes to `axom.treasury_status` for the dashboard. Companies that never enabled yield cost no RPC calls.
- **RY-07a Nonces.** Payouts and treasury moves share the treasury key. Both take the higher of the chain's reported nonce and the highest nonce signed here across `axom.payouts.tx_nonce` and `axom.treasury_moves.tx_nonce`, since NEAR reports a key's nonce a couple of blocks late.
- **RY-08 Self-healing.** A supply whose `ft_on_transfer` fails is refunded by the wNEAR contract, and a failed withdrawal transfer is re-credited by Rhea; the transaction can still report success. The planner doesn't trust move results: it re-reads the position every time, so refunded wNEAR is unwrapped and the floor is restored on the next ticks.
- **RY-09 Units.** Yocto amounts are serialised as decimal strings in every JSON the planner writes (`near::yocto_str`): JSONB round trips and JavaScript lose precision above 2^53.
- **RY-10 Dashboard.** `GET /admin/treasury/yield` (MFA admin, database only): on/off, rules, the latest plan (liquid, supplied, floor, target, APR, reason), interest so far (supplied now + withdrawn − supplied in), the last 20 moves with NearBlocks links. Overview card "Treasury yield".
